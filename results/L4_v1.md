# L4, kernel v1: results against the predictions

**Setup:**
- Colab NVIDIA L4, torch 2.11 + CUDA 13.0, Triton 3.6. The local tests used Triton 3.9.
- M = 1, group size 128.
- Measured copy bandwidth is 231 GB/s (spec 300 GB/s); it is the 100% line below.
- Raw data: [`gemv_NVIDIA_L4_m1_v1.json`](gemv_NVIDIA_L4_m1_v1.json).
- Every Triton result matched the reference to 2.3e-4 to 4.3e-4 relative error, so the kernel is correct on the GPU.

**How to read the table:**
- *Programs* is the number of Triton programs the kernel launches: N / BLOCK_N for the best config.
- *K steps* is how many 128-column steps each program walks.
- int4 bandwidth counts the bytes the kernel actually reads: codes, scales, zero points, x and y.

## What limits v1

int4 bandwidth tracks the number of programs, not the work per program:

| Programs | int4 % of copy BW |
|---|---|
| 16 | 4% |
| 32 | 9% |
| 96 | 18–23% |
| 224 | 30–43% |
| 560 | 48% |

Three more observations:
- The config sweep chose the smallest BLOCK_N it was offered (16) for 9 of 10 layers, which means it maximised the program count.
- At equal program count, the longer loop does better: `down` reaches 43% with 148 K steps, against 30% for q/o_proj with 28 steps.
- The two `kv_proj` layers launch 16 and 32 programs on a 58-SM GPU, and they are slower than fp16.

Together this points to too little parallelism. An SM running 3–4 programs with 2–4 warps each does not keep enough loads in flight to saturate DRAM. Unpacking does not look like the limit, as it was on the A53, because then speed would not depend on how the rows are split across programs.

**Next experiment (v2):** split K across programs and reduce the partial sums. If the parallelism explanation is right, kv_proj, q/o_proj and the 1.5B layers should move toward the gate_up level. If they do not, the inner loop is the limit, and the next step is Nsight Compute.

## Predictions for v2, written before running it (2026-11-01)

v2 adds split-K. The sweep offers splits of 1–16 and BLOCK_N down to 8. The same run also times the best config without split-K, so v1 and v2 are compared on the same GPU instance.

| # | Prediction | Would be wrong if |
|---|---|---|
| Q1 | Both `kv_proj` layers become faster than fp16 (from 0.63–0.68× to > 1×) | either stays ≤ 1× |
| Q2 | 7B q/o_proj reach ≥ 2× over fp16 (from 1.5×) | < 1.8× |
| Q3 | Every large 7B layer reaches ≥ 50% of copy bandwidth | any is below 50% |
| Q4 | 7B gate_up gains little (< 15%), because it already has enough programs | it gains ≥ 15% |
| Q5 | The best split always gives ≥ 400 programs (about 7 per SM) | a winner has < 400 programs |
